Automatiser la sauvegarde

Deux choses à sauvegarder : la base de données et le dossier de l'application (fichiers uploadés, personnalisations). Les exemples ci-dessous utilisent des chemins génériques — adaptez-les à votre installation.

XAMPP / Windows — script .bat + Planificateur de tâches

@echo off
set DATE=%date:~-4%-%date:~3,2%-%date:~0,2%
set DEST=C:\Backups\AssetFlow\%DATE%
mkdir "%DEST%"

:: export de la base (chemin XAMPP par défaut)
C:\xampp\mysql\bin\mysqldump -u root assetflowcrm_db > "%DEST%\espocrm.sql"

:: archive des fichiers de l'application
powershell Compress-Archive -Path "C:\xampp\htdocs\assetflow\*" -DestinationPath "%DEST%\espocrm_files.zip"

:: copie vers un dossier de sauvegarde / disque externe / NAS
robocopy "%DEST%" "D:\Sauvegardes\AssetFlow\%DATE%" /E

Planifier ce script avec le Planificateur de tâches Windows pour qu'il s'exécute chaque jour à heure fixe.

Docker / Linux — export depuis les conteneurs

# dump de la base
docker exec espocrm-db mysqldump -u espocrm -pchangeme espocrm > backup.sql

# archive du volume applicatif (fichiers, uploads, config)
docker run --rm -v espocrm:/data -v $(pwd):/backup alpine \
  tar czf /backup/espocrm_files.tar.gz -C /data .

Ces deux commandes se planifient aussi bien avec le Planificateur de tâches (Windows) qu'avec cron (Linux/Mac), en les regroupant dans un petit script.

Où stocker la copie — gardez toujours une copie hors de la machine qui héberge l'application (disque externe, NAS, autre machine) : une sauvegarde stockée uniquement sur le même disque ne protège pas contre une panne matérielle.
Sauvegarde — copie distante

Copier les sauvegardes sur un NAS (TrueNAS)

Un NAS dédié permet de garder une copie des sauvegardes sur une machine physiquement séparée du serveur applicatif. TrueNAS (Community Edition) est une option gratuite et open source pour ça. Le principe ci-dessous est générique — adaptez les adresses et noms à votre propre réseau.

  1. Installer TrueNAS sur une machine séparée

    Idéalement un second PC ou un petit serveur dédié, distinct de celui qui héberge Espo. Lui attribuer une adresse IP fixe sur le réseau local (par exemple 192.168.1.x) pour qu'elle ne change pas.

  2. Créer un pool puis un dataset dédié

    Dans l'interface web de TrueNAS, créer un pool à partir du ou des disques réservés aux sauvegardes, puis un dataset à l'intérieur (par exemple backups/assetflow) pour isoler les fichiers de ce projet des autres sauvegardes éventuelles.

  3. Activer un partage réseau sur ce dataset

    Activer un partage SMB (compatible Windows) ou NFS (Linux/Mac) sur le dataset, avec des identifiants dédiés à la sauvegarde plutôt que le compte administrateur de TrueNAS.

  4. Monter le partage depuis le serveur applicatif

    Sous Windows, mapper le partage comme un lecteur réseau (par exemple Z:) avant de lancer le script de sauvegarde, ou l'ajouter directement dans le chemin de destination du script .bat (\\192.168.1.x\backups\assetflow\).

  5. Adapter le script de sauvegarde

    Reprendre le script .bat plus haut et remplacer la ligne robocopy par une copie vers le partage TrueNAS monté, par exemple :

    :: copie vers le partage TrueNAS (adapter le chemin réseau)
robocopy "%DEST%" "\\192.168.1.x\backups\assetflow\%DATE%" /E
Pourquoi séparer le NAS du serveur applicatif — si le disque du serveur Espo tombe en panne ou si la machine est compromise, la copie sur le NAS reste intacte. C'est aussi l'occasion de tester une restauration complète sans toucher à l'environnement de production.
Vérifier après coup — après avoir mis en place la copie automatique, ouvrez régulièrement l'interface TrueNAS pour confirmer que les nouveaux fichiers datés arrivent bien chaque jour, et pas seulement que le script tourne sans erreur.

Restaurer une sauvegarde

  1. Recréer la base si besoin

    Créer une base vide, puis importer l'export : mysql -u root assetflowcrm_db < espocrm.sql

  2. Restaurer les fichiers

    Extraire l'archive dans le dossier du site (htdocs/assetflow ou le volume Docker), en écrasant les fichiers existants.

  3. Vérifier la configuration

    Contrôler que data/config.php pointe bien vers la base restaurée (nom, utilisateur, mot de passe).

  4. Tester la connexion

    Ouvrir l'application et vérifier qu'un compte de chaque rôle peut se connecter et voir ses données.

Conseil — tester une restauration complète de temps en temps vaut mieux que de découvrir un problème le jour où on en a réellement besoin.
